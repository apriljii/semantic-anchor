第一幕 · 为什么
Core Thesis

最不可控的不是语法，是语义

语法错误有编译器兜底；语义错误——命名漂移、枚举编造、敏感未脱敏——代码能跑，但引用是错的。Prompt 是软约束，结构化契约才可被验证。

已解决

语法错误

编译器 / LSP 拦截。类型不匹配、未定义变量，构建即失败。

未解决

语义错误

sym 代替 ticker，side 写成 long 而非 buy，资金账号未 masked——没人拦。

第二幕 · 是什么
Formula

语义锚 = 锚 + 链 + 抛锚 + 绷紧

四块公式，缺一不可。§2.1–2.4 逐块构成 SemanticAnchor；没有 verify，就没有「锚」，只有「建议」。

锚 ID+ 链 Contract+ 抛锚 Inject+ 绷紧 Gate
§2.1

锚 · Canonical ID

约束什么：命名实体引用。ticker、order_side、submitOrder——只管引用，不管逻辑。

kind: field / enum / signature
§2.2

链 · Contract

契约长什么样：ConstraintUnit。类型、枚举、pattern、provenance、负面清单。

constraints.json
§2.3

抛锚 · Inject

事前进 context：resolve → bind bundle。best-effort，miss 不编造。

resolve · bind_constraints
§2.4

绷紧 · Gate

事后裁决：verify → violation / feedback → retry 收敛。must-have 压舱石。

verify_usage

结构契约 · ConstraintUnit 长什么样？

协议的灵魂是 ConstraintUnit——把「规范 id」绑到「可验证契约」上的一行 JSON。 verify_usage 不做推理，只拿生成物里的 name / value / call 与这张卡片对照。

原子 · field（来自 examples/quant/constraints.json）
{
  "id": "ticker",              // 锚：规范 id（verify 期望的名字）
  "kind": "field",
  "aliases": ["sym", "symbol", "标的"],  // resolve：sym → ticker
  "type": "string",
  "provenance": "declared",    // 来源：declared / derived / emergent
  "constraints": {             // 链：可机器验证的形状
    "required": true,
    "pattern": "^[A-Z0-9.]{1,12}$"
  },
  "policies": []               // 策略：如 sensitive → 须 masked
}
  • ① id + aliases

    resolve / bind 用：把任务里的「标的」「sym」认成 ticker。verify 发现用了 sym 而非 ticker → NON_CANONICAL_NAME（drift）。

  • ② constraints + policies

    verify 用：值 aapl 不符合 pattern → PATTERN；枚举 long 不在 [buy,sell] → ENUM；敏感字段未脱敏 → SENSITIVE_NOT_HANDLED。

  • ③ provenance · 谁写的？

    declared 人手 / 治理平台；derived 从 TS / OpenAPI 扫描；emergent 会话临时补。语义锚不发明标准名，只执行已有契约。

  • ④ 只有 Contract 不够

    光有这张卡片 = 户口簿（查表）。加上 verify_usage 闭环 = SemanticAnchor。没有 verify，就没有「锚」，只有「建议」。

复合 · signature（API 入口，members 引用原子 unit）
{
  "id": "submit_order",
  "kind": "signature",
  "aliases": ["placeOrder", "报单"],
  "provenance": "derived",       // 从 oms-api.ts 扫描
  "members": [
    { "role": "param", "ref": "ticker", "position": 0 },
    { "role": "param", "ref": "order_side", "position": 1 },
    { "role": "returns", "ref": "order_id" }
  ]
}
verify 对照什么？ 从生成代码抽出结构化 usages，例如 { name: "sym", value: "aapl" }、 { name: "placeOrder", kind: "call" }—— 逐条与 ConstraintUnit 比对，输出可回注 Agent 的 violation / feedback（见 Walkthrough）。

第三幕 · 为什么必须这样
Foundation

开放世界不能只有 Inject

户口簿是封闭世界的退化特例——Inject（查表）≈ 保证。开放世界 miss 是常态，必须补上 Gate，可靠性压在 verify 上。

维度户口簿（封闭）SemanticAnchor（开放）
作用点输入解析 resolve行动守门 verify
miss 语义异常 → 补录飞轮常态 → verify 兜底
验证真理协议自洽（查表即对）环境裁决（编译器/测试）
多 Agent handoff：Planner 的 bind_constraints bundle 是传给 Coder 的标准契约载体。没有它，ticker / order_side 约束在 handoff 时丢失，语义漂移重现。

Quick Start

安装与使用

SemanticAnchor 是挂在你现有 Agent 工作流上的语义守门员，不是独立 App。Harness 工程师请先读 Harness 集成指南；下面是从安装到第一次调用的步骤。

注入是优化，守门是保证。 没有 verify，约束只是「建议」；开放世界任务必须跑 bind → act → verify → retry 闭环。

一、安装

需要 Node.js 18+ 与 npm。克隆仓库、安装依赖，并用 demo 确认环境正常。

# 1. 获取代码
git clone <repo-url> semantic-anchor
cd semantic-anchor

# 2. 安装依赖（MCP Server + 协议实现）
npm install

# 3. 验证（可选，确认协议与 demo 可跑）
npm test
npm run demo        # 应看到 9 → 0 碰撞测试

二、使用方式 A · MCP 接入（IDE / CLI Agent）

把 src/server.js 注册为 MCP Server。Agent 通过宿主（Cursor、Claude Desktop、VS Code Copilot 等）自动调用四个工具。同一 Server 块，按宿主 schema 写入对应配置文件即可。

  1. 配置 MCP Server

    项目已含 .cursor/mcp.json 与 .vscode/mcp.json。在其他机器或宿主上，把路径改为绝对路径（Claude Desktop 不支持相对路径）：

    # Cursor · .cursor/mcp.json
# Claude Desktop · ~/Library/Application Support/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "semantic-anchor": {
      "command": "node",
      "args": ["/absolute/path/to/semantic-anchor/src/server.js"],
      "env": {
        "SA_CONSTRAINTS": "/absolute/path/to/constraints.json"
      }
    }
  }
}

    SA_CONSTRAINTS：单个 JSON 文件，或包含多个 *.json 的目录。Demo 可用 examples/quant/constraints.json。

  2. 重启宿主并确认工具出现

    保存配置后重启 MCP 宿主。在 Agent 对话的工具列表中应看到 semantic-anchor 下的 4 个工具：

    resolve · get_constraint · bind_constraints · verify_usage

    调试：终端运行 npm run mcp，stderr 应输出 loaded N constraint unit(s)。

  3. 准备你自己的约束（生产用法）

    把 SA_CONSTRAINTS 指向你项目的字段/枚举/API 契约。格式见 ConstraintUnit Schema，可参考 examples/quant/constraints.json 编写。

  4. Agent 工作流（两卡口）

    ① 任务开始 bind_constraints({ aliases: ["ticker", "order side", …] }) → bundle 注入 context（declared → system prefix） ② 生成代码后、写文件前 verify_usage({ usages: [...] }) → ok：放行写盘 / commit → !ok：读 feedback → 修改 → 再 verify（通常 1 次 retry 收敛）

  5. 试一句对话（Cursor / Claude Desktop Agent）

    用 semantic-anchor MCP：先 bind_constraints 绑定限价报单相关字段（ticker、order side、quantity、account、limit price），生成 submit order 函数，从代码抽取 usages 后 verify_usage，有 violation 就按 feedback 改到达标。

常见 MCP 宿主与配置文件：

Cursor.cursor/mcp.json 或 ~/.cursor/mcp.json
Claude Desktopclaude_desktop_config.json → 顶层 mcpServers，需完全退出后重启
VS Code + Copilot.vscode/mcp.json，Copilot Agent 模式下使用
Windsurf~/.codeium/windsurf/mcp_config.json
Cline / Continue扩展 MCP 设置 或 ~/.continue/config.json

三、使用方式 B · 嵌入自研 Harness / CI

不走 MCP、直接在 Node 进程里调用协议。适合自研 Agent loop、CI 守门、或不想依赖 IDE 的场景。

  1. 引入 semantic-gate 中间件

    const { createStore } = require('./src/protocol/constraint-store');
const { createSemanticGate } = require('./examples/harness-hook/semantic-gate');

const store = createStore();
store.load(require('./examples/quant/constraints.json');
const gate = createSemanticGate(store);

  2. 事前 bind + 事后 enforce

    // 任务开始：注入 bundle
gate.bind({ aliases: ['ticker symbol', 'order side', …], extraConstraints });

// 模型生成后：verify + retry 直到通过
const outcome = await gate.enforce(usages, {
  retry: (feedback) => modelFixAndReturnUsages(feedback),
});
if (outcome.ok) { /* 写文件 / 跑测试 */ }

  3. 跑通演示

    npm run demo:harness   # bind → enforce → retry
npm run demo:derived   # TS 派生约束 + gate

    参考 design.md §2.1 · examples/harness-hook/semantic-gate.js

第一幕 · 为什么
Core Thesis

最不可控的不是语法，是语义

语法错误有编译器兜底；语义错误——命名漂移、枚举编造、敏感未脱敏——代码能跑，但引用是错的。Prompt 是软约束，结构化契约才可被验证。

已解决

语法错误

编译器 / LSP 拦截。类型不匹配、未定义变量，构建即失败。

未解决

语义错误

sym 代替 ticker，side 写成 long 而非 buy，资金账号未 masked——没人拦。

第二幕 · 是什么
Formula

语义锚 = 锚 + 链 + 抛锚 + 绷紧

四块公式，缺一不可。§2.1–2.4 逐块构成 SemanticAnchor；没有 verify，就没有「锚」，只有「建议」。

锚 ID+ 链 Contract+ 抛锚 Inject+ 绷紧 Gate
§2.1

锚 · Canonical ID

约束什么：命名实体引用。ticker、order_side、submitOrder——只管引用，不管逻辑。

kind: field / enum / signature
§2.2

链 · Contract

契约长什么样：ConstraintUnit。类型、枚举、pattern、provenance、负面清单。

constraints.json
§2.3

抛锚 · Inject

事前进 context：resolve → bind bundle。best-effort，miss 不编造。

resolve · bind_constraints
§2.4

绷紧 · Gate

事后裁决：verify → violation / feedback → retry 收敛。must-have 压舱石。

verify_usage
第三幕 · 为什么必须这样
Foundation

开放世界不能只有 Inject

户口簿是封闭世界的退化特例——Inject（查表）≈ 保证。开放世界 miss 是常态，必须补上 Gate，可靠性压在 verify 上。

维度户口簿（封闭）SemanticAnchor（开放）
作用点输入解析 resolve行动守门 verify
miss 语义异常 → 补录飞轮常态 → verify 兜底
验证真理协议自洽（查表即对）环境裁决（编译器/测试）
多 Agent handoff：Planner 的 bind_constraints bundle 是传给 Coder 的标准契约载体。没有它，ticker / order_side 约束在 handoff 时丢失，语义漂移重现。
第四幕 · 怎么落地
Implementation

四动词 = 构成的 MCP 映射

4 个工具是第二幕四块的操作化，不是另起一套概念。注入是优化，守门是保证。

resolve best-effort

别名 → 规范 id。miss → unresolved + 候选。

→ §2.1 锚 · 解析面
get_constraint 查询

取完整 ConstraintUnit：类型、枚举、策略。

→ §2.2 链 · 读契约
bind_constraints 注入

打包 bundle + 注入位置指引（system prefix / JIT）。

→ §2.3 抛锚
verify_usage must-have

契约 + 环境裁决 → 结构化 feedback。

→ §2.4 绷紧

抛锚

bind bundle 注入 context

bind_constraints

行动

模型生成 usages / 代码

绷紧

verify 裁决 + feedback

verify_usage

收敛

回注 → retry → 0 错误

附录 · 快速开始
Quick Start

快速开始

安装依赖后，一条命令预览 Demo 报告，或启动 MCP 服务接入 Cursor。

# 安装
npm install

# 预览本页 + 终端 Demo
npm run preview   # → http://localhost:4173
npm run demo      # 终端碰撞测试

# MCP 服务（Cursor 自动拉起）
npm run mcp
# .cursor/mcp.json
{
  "mcpServers": {
    "semantic-anchor": {
      "command": "node",
      "args": ["src/server.js"],
      "env": {
        "SA_CONSTRAINTS": "examples/quant/constraints.json"
      }
    }
  }
}

30 秒电梯演讲

AI 写代码时，语法错误编译器会拦，语义错误没人拦——sym 代替 ticker、long 代替 buy、调用不存在的 API，代码能跑但引用是错的。

SemanticAnchor 是一个引用级约束协议：把命名实体（字段、枚举、符号、签名）锚到可验证契约上，通过 事前注入 + 事后守门 + 结构化 feedback 让 Agent 输出收敛。我们在量化限价报单场景做了碰撞测试：Prompt-only 7 个语义错误全部交付，加协议闭环后 0 个。

它不是 Compass 开源版，而是从生产 field-registry 提炼的方法论 + MCP 参考实现；完整 prompt→代码 体验在 Compass + OpenSpec 全栈里，SemanticAnchor 是 Apply 阶段的语义守门子层。

核心公式（必背）

语义锚 = 锚（Canonical ID） + 链（Verifiable Contract） + 抛锚（Inject） + 绷紧（Gate）

  锚          链                    抛锚                  绷紧
  约束什么    ConstraintUnit        resolve/bind          verify/feedback
              形状/枚举/策略         best-effort           must-have
注入是优化，守门是保证没有 verify，只有「建议」，不是「锚」。
窄腰原则只约束「引用」（名、形、值、策略），不约束逻辑、控制流、业务规则。

引用谱系 kind

field → param → enum → symbol → signature / endpoint（复合用 members[]）

provenance 三分法

值含义例子
declared预注册、人工策展户口簿、OpenAPI、8维 schema 编译
derived从项目空间派生TS 签名、LSP、eslint
emergent会话累积用户中途说「保持向后兼容」

迁移叙事（40/60 · 面试金句）

「Compass field-registry 是 SemanticAnchor 在封闭世界、金融域的生产实现；SemanticAnchor 是把『命名实体引用 + 可验证契约 + 注入守门闭环』提炼成领域无关的参考协议。

户口簿解决的是『别名能不能对上』；SemanticAnchor 解决的是『Agent 生成物有没有越界』——后者需要 verify 和环境裁决，这是迁移里 60% 的新工程。」

高频问答

和 LSP / TypeScript 什么关系？

LSP/tsc 是 verify 的环境裁决来源之一，不是替代品。SemanticAnchor 额外覆盖契约级语义：枚举合法值、pattern、敏感策略、symbol 存在性——编译器不管 sym vs ticker 的 drift。

和 OpenSpec / Spec-Driven 什么关系？

OpenSpec 管变更怎么流、测什么（Apply 之前 + E2E）；SemanticAnchor 管 Apply 时生成物引用别漂。嵌在 /opsx:apply 执行路径里，是子层不是竞品。

为什么不把 8 维 compile 做进 SemanticAnchor？

8 维是 Compass「雅」层 + OpenSpec 交付面，属于低代码场景全栈契约。SemanticAnchor 只消费其中「引用级」切片（schema.json + api.json），通过 adapter 派生 ConstraintUnit，不复制 8 维文件。扩边界会破坏窄腰和开源定位。

多 Agent 为什么需要 bundle？

Planner 解析到的 ticker/order_side 契约，若无标准 bundle handoff，Coder 退回 prompt 软约束 → 语义漂移重现。bind_constraints 输出是 Planner→Coder 的标准契约载体。碰撞测试：examples/multi-agent/demo.js。

MCP 和 Library 嵌入怎么选？

MCP：已有 MCP 宿主（Cursor/Claude Desktop），快速试验，Agent 自主调工具。
Library：自研 Harness/CI，要强控 gate 时机和 retry，用 semantic-gate 中间件。
生产常见：混合——Harness 内 enforce，MCP 供 IDE 联调。

verify 的 usages 从哪来？

生产三条路：AST/LSP 从生成物解析；Agent 输出结构化 field manifest；Hybrid（模型 draft + AST 校正）。协议只定义 usages 结构，不做语言级 parser。

刁钻问题（基于真实讨论）

「用户要装很多 npm 包才能串起来，不像完整方案？」

承认感受，澄清定位。

SemanticAnchor 本身依赖极少（MCP SDK），琐碎感来自故意不做完整产品——它是 Harness 内的语义守门芯片，不是 prompt→代码 全家桶。

完整体验应在 Compass Apply 里收口：OpenSpec 驱动变更 → 8维+户口簿 compile → 内嵌 semantic-gate → E2E。用户跑 /opsx:apply，零感知 SemanticAnchor。

开源 repo 定位是工程验证报告（证明 7→0），给 Harness 工程师参考协议，不是给业务用户装的 App。

「只有一个 schema 契约，流程串不起来？」

ConstraintUnit schema 只是四块公式里的「链」。串流程缺的是桥接层（8维→constraints、prompt→aliases、代码→usages），应在 Compass 私有栈建，不应膨胀 SA 协议。

分层：上游产约束 → SA 守门 → 环境裁决。SA 管 Apply 中/后的引用面，不管 propose/compile。

「为什么从 16 个工具减到 4 个？」

16 个是 Compass 产品面（search_fields、suggest_field、compile_schema…）。开源协议遵循最小化：4 个动词完整覆盖 锚+链+Inject+Gate 闭环。其余能力要么合并（check_sensitive→verify），要么 Non-Goal（低代码 compile）。

「开放世界 miss 了怎么办？」

miss 是常态，不是错误。resolve 返回 unresolved + 候选，不编造。unverifiable 报告但不硬失败。真正可靠的是 verify + 环境裁决兜底，不是提高 resolve 命中率。

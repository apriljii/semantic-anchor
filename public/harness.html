For Harness Engineers

Harness 集成指南

SemanticAnchor 是 Agent Harness 内的语义约束子层——在 loop 里加 bind + verify 两个卡口， 拦住「能编译但引用错了」的 silent failure。不是完整 Coding Agent，不是字段字典。

完整 Markdown：docs/harness-integration.md · MCP 宿主配置：mcp-integration.md · 设计权威：design.md

1 · 在 Harness 栈里的位置

┌──────────────────────────────────────────────────────────┐ │ 项目级 Harness（orchestration · sandbox · test · loop） │ │ ┌────────────────────────────────────────────────────┐ │ │ │ SemanticAnchor — 语义约束子层 │ │ │ │ resolve · bind_constraints · verify_usage │ │ │ └────────────────────────────────────────────────────┘ │ └────────────────────────────┬─────────────────────────────┘ ↓ 环境裁决：tsc / LSP / pytest / E2E

✓ 是什么

Harness 内的 semantic gate；4 动词 MCP + 参考实现；可复现工程验证报告（9→0）。

✗ 不是什么

完整 Agent runtime、字段字典、低代码、Compass/OpenSpec 替代品、规则引擎。

只约束引用面：命名存不存在、叫什么、类型/形状/合法值、敏感策略。不约束业务逻辑与控制流。

2 · 要拦的 failure mode

语法错误有编译器兜底。语义错误代码能跑、能编译，但引用是错的——Harness 若只有 prompt + 一次生成，这些会 silent ship。

类型例子编译器SemanticAnchor
命名漂移sym → 应为 ticker不管DRIFT
枚举编造long → 应为 buy不管ENUM
格式错aapl → AAPL不管PATTERN
幻觉 APIplaceOrder() 不存在可能 tscSYMBOL_NOT_FOUND
敏感泄露account 明文 log不管SENSITIVE_NOT_HANDLED

真实 TypeScript 产物：walkthrough · naive → draft → fixed

3 · Agent loop：两个卡口

用户任务（自然语言） │ ▼ ┌─ 卡口 ① 事前 · bind（best-effort）──────────────────┐ │ 提取 aliases → bind_constraints │ │ → bundle 注入 context（declared → system prefix） │ └──────────────────────────┬───────────────────────────┘ ▼ 模型生成代码 / tool calls │ ▼ ┌─ 卡口 ② 事后 · verify（must-have）──────────────────┐ │ 抽取 usages → verify_usage │ │ → ok：放行写盘 / commit │ │ → !ok：feedback → 模型修改 → 再 verify │ └──────────────────────────┬───────────────────────────┘ ▼ 环境裁决（tsc / test / sandbox）
卡口 ② 不可跳过。 长 system prompt 不能替代行动后验证。

多 Agent handoff

Planner 的 bind_constraints bundle 是传给 Coder 的标准契约载体。没有 bundle，handoff 时 ticker / order_side 约束丢失，语义漂移重现。

4 · 集成方式

4.1 方式 A · MCP（IDE / CLI Agent 宿主）

启动 src/server.js（stdio），宿主在 Agent 对话中调用四工具。同一 Server 块可接 Cursor、Claude Desktop、VS Code Copilot、Windsurf 等。

.cursor/mcp.json · claude_desktop_config.json · …
{
  "mcpServers": {
    "semantic-anchor": {
      "command": "node",
      "args": ["/absolute/path/to/semantic-anchor/src/server.js"],
      "env": {
        "SA_CONSTRAINTS": "/absolute/path/to/constraints.json"
      }
    }
  }
}
工具卡口职责
resolve①别名 → 规范 id；miss → unresolved，不编造
get_constraint①读单个 ConstraintUnit
bind_constraints①打包 bundle + system prefix / JIT 指引
verify_usage②契约裁决 → violation / feedback

适用 已有 MCP 宿主、Agent 自主调工具、快速试验。
详表：docs/mcp-integration.md · 示例：config/mcp/examples/

4.2 方式 B · Library 嵌入（自研 Harness / CI）

在 loop 代码里直接调中间件，Harness 强制 gate 时机，不依赖 Agent 记得调 MCP。

examples/harness-hook/semantic-gate.js
// npm run demo:harness
const { createStore } = require('./src/protocol/constraint-store');
const { createSemanticGate } = require('./examples/harness-hook/semantic-gate');

const store = createStore();
store.load(require('./examples/quant/constraints.json'));
const gate = createSemanticGate(store, { maxRetries: 3 });

// 卡口 ①
const { bundle, injection } = gate.bind({
  aliases: ['ticker symbol', 'order side', 'quantity', 'account'],
  extraConstraints: [],
});

// ... model generates → extract usages ...

// 卡口 ②
const outcome = await gate.enforce(usages, {
  retry: async (feedback, attempt) => modelFixUsages(feedback),
});

if (!outcome.ok) throw new Error('semantic gate blocked write');
// 才允许 write_file / commit

适用 自研 Harness、CI 守门、强控 retry、生产 loop。

底层单一事实来源：src/dispatch.js（MCP server 与 demo 共用）。

4.3 方式 C · 混合（生产常见）

阶段做法

Coder注入 bundle；生成后 Harness 强制 gate.enforce()

5 · 约束数据（SA_CONSTRAINTS）

constraints.json = { "units": [ ConstraintUnit, ... ] }。格式：constraint-unit.schema.json。示例：examples/quant/constraints.json

provenance来源放哪
declaredschema 编译、OpenAPI、手写户口簿SA_CONSTRAINTS 主文件
derivedTS 签名、LSP、OpenAPI 扫描bind({ extraConstraints })
emergent会话追加（「保持向后兼容」）会话 store / register

有 Spec 体系时的推荐流水线

pm.md / spec.md → 编译链 → schema.json (+ api.json) ↓ transform（引用级切片） constraints.json → SA_CONSTRAINTS Apply 时 TS 扫描 → extraConstraints（derived）

本 repo 未包含 Compass 编译链；可手写 constraints 或自建 transform。校验：npm run validate:spec

6 · usages：verify 的输入

verify_usage 消费结构化 usages，不是 raw 源码。符号调用必须 "kind": "call"。

verify_usage 输入示例
{
  "usages": [
    { "name": "ticker", "value": "AAPL" },
    { "name": "order_side", "value": "buy" },
    { "name": "account_id", "value": "ACC****5678", "masked": true },
    {
      "name": "submit_order",
      "kind": "call",
      "args": [
        { "name": "ticker" },
        { "name": "order_side" }
      ]
    }
  ]
}

生产抽取（demo 用预定义映射）

方式说明
AST / LSP从 TS/JS 生成物解析字段赋值、call expression
Agent manifest模型输出结构化 field list（需约束输出 schema）
Hybrid模型 draft + AST 校正
本 repo demo 用 scenario 预定义 usages 保证无 API Key、100% 可复现。生产 Harness 必须补抽取层——这是集成的主要工程量之一。

7 · derived 约束（开放世界 API）

静态 constraints 通常只有 declared 字段/枚举。项目内 API 签名应运行时派生后传入 bind：

examples/derived/scan-typescript.js · npm run demo:derived
const { deriveFromTypescript } = require('./examples/derived/scan-typescript');
const derived = deriveFromTypescript('./artifacts/oms-api.ts');

gate.bind({
  aliases: [...mentioned, 'submit order'],
  extraConstraints: derived,
});

8 · 环境裁决（与 tsc 分工）

层验证什么

9 · 接入检查清单

MVP

  • constraints.json 覆盖任务相关 field / enum
  • 写文件前强制 verify_usage
  • violation → structured feedback → 模型 retry
  • retry 上限（如 3 次）
  • npm run demo:harness 本地跑通

生产加强

  • usages 从 AST/LSP 抽取
  • derived 扫描 TS/OpenAPI 补 signature
  • Planner→Coder bundle handoff 标准化
  • tsc/test 接入 environment
  • 约束变更走 schema/transform SSOT
  • metrics：shipped semantic errors、retry 次数、violation 码分布

11 · FAQ

和 LSP / type checker 什么关系？

LSP 是 environment 来源之一。SemanticAnchor 额外覆盖契约级语义（枚举、pattern、敏感、symbol），编译器不覆盖。

和 OpenSpec 什么关系？

OpenSpec 管变更怎么流、测什么；SemanticAnchor 管 Apply 时引用别漂。应串联。详见 ecosystem.html（可选阅读，非集成必需）。

规则引擎要写进 ConstraintUnit 吗？

不要。 业务阈值、跨实体规则是 Non-Goal。只描述引用形状。

MCP 还是 Library？

选 MCP选 Library
已有 MCP 宿主、快速试验自研 Harness、CI、强控 gate

verify 全 unverifiable？

检查 usages 的 name 是否对齐 constraints；symbol 是否带 kind: "call"；store 是否有 signature 单元。

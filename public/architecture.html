Architecture · v1

SemanticAnchor 架构设计讲述

引用级约束协议 — 让 AI Agent 对「命名实体引用」的理解与生成，可控、可验证、可收敛。

叙事结构：公式分解法 · 权威来源 docs/design.md

第一幕 · §0

一句话 + 边界

SemanticAnchor 是一个引用级约束协议。它让 AI Agent 在开放世界任务中，对「命名实体的引用」变得可控、可验证、可收敛。

✓ 是什么

Harness 语义约束子层；ConstraintUnit 协议 + MCP 参考实现 + 碰撞测试报告。

✗ 不是什么

不是字段字典、低代码、Compass 开源版、项目级 Harness。

第一幕 · §1

核心命题

AI 生成代码时，最不可控的不是语法，是语义。语义可控的最小化工程手段，是结构化契约，而不是 Prompt。

错误类型例子现状
语法错误括号不匹配、类型不匹配编译器 / LSP 已解决 ✓
语义错误sym 代替 ticker；side 写成 long；幻觉 OMS 函数没人拦 ✗

Prompt 是概率性软约束。结构化契约是工程性硬约束——可解析、可注入、被验证。

第二幕 · §2

语义锚的构成（总览）

全文主轴：语义锚 = 锚 + 链 + 抛锚 + 绷紧。§2.1–2.4 逐块讲完；读完本节即可独立解释 SemanticAnchor 是什么。

  锚（Anchor）          链（Contract）           抛锚（Inject）         绷紧（Gate）

  Canonical ID    +   Verifiable Contract   +   resolve / bind    +   verify / feedback
  规范名「钉」          形状/枚举/策略            best-effort 注入        must-have 守门
      │                      │                      │                      │
      └──────────────────────┴──────────────────────┴──────────────────────┘
                                    = 语义锚（Semantic Anchor）
构成回答性质
2.1 锚约束什么核心对象
2.2 链契约长什么样ConstraintUnit
2.3 抛锚事前怎么进 contextbest-effort
2.4 绷紧事后怎么裁决must-have

没有 verify，就没有「锚」，只有「建议」。注入是优化，守门是保证。

§2.1

锚 · Canonical ID

约束对象 = 命名实体的引用。模型从意图到实现的每一步绑定，都是语义幻觉的入口。

意图空间                          实现空间
─────────────────────────────────────────────────────────────
"标的代码"            ──绑定──▶   ticker : string, pattern=^[A-Z0-9.]+$
"买卖方向"            ──绑定──▶   order_side : enum[buy|sell]
"限价报单"            ──绑定──▶   submitOrder(ticker, side, qty, ...) -> order_id

引用谱系（kind）

kind量化例子类型
fieldticker原子
paramquantity原子
enumorder_side原子
symbolsubmitOrder原子
signaturesubmitOrder(...)复合

窄腰原则

✓ 约束引用

存不存在 · 叫什么 · 类型/形状/合法值 · 跨上下文映射

✗ 不约束逻辑

撮合算法 · 控制流 · 架构决策 · 函数内部算不算对

在 Harness 中的位置

┌─────────────────────────────────────────────┐
│  项目级 Harness（Claude Code 等）               │  repo / shell / test / loop
│  ┌───────────────────────────────────────┐  │
│  │  SemanticAnchor（语义约束子层）             │  │  resolve / bind / verify
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
§2.2

链 · Verifiable Contract

ConstraintUnit 把命名引用绑到可验证契约上。协议 Schema 规定「标准长什么样」；实例数据是「某条标准的具体内容」。

三种 Schema — 必须分清

名称文件在本项目
协议 Schemaconstraint-unit.schema.json✅ 元规范
约束实例examples/quant/constraints.json✅ 数据
Compass 业务 Schemapage/ui/api…❌ Non-Goal
 
{
  "id": "ticker",
  "kind": "field",
  "aliases": ["symbol", "sym", "标的"],
  "type": "string",
  "provenance": "declared",
  "constraints": { "pattern": "^[A-Z0-9.]{1,12}$" }
}

provenance（约束从哪来）

provenance来源例子
declared人工策展户口簿、OpenAPI、命名规范
derived项目空间派生TS 类型、LSP 符号表
emergent会话累积「保持 API 向后兼容」
—无标准→ unresolved / unverifiable，不编造

原子 vs 复合

{
  "id": "submit_order",
  "kind": "signature",
  "members": [
    { "role": "param", "ref": "ticker" },
    { "role": "param", "ref": "order_side" },
    { "role": "returns", "ref": "order_id" }
  ]
}

constraints 负面清单：禁止业务阈值 · 跨实体规则 · 时变策略 → 属于 Compass 规则引擎（达层）。

事前：检索任务相关约束 → 打包 bundle → 注入 context，提高首次正确率。

原则含义
任务相关才 bind不全库灌 context
resolve 允许 missmiss → unresolved + 候选，不编造

§2.4

绷紧 · Gate

事后：验证生成物 → 结构化 feedback → 重试收敛。开放世界可靠性的压舱石。

模型 act（生成 usages）
         │
         ▼
   verify_usage
         │
    ┌────┴────┐
  通过      违反 → feedback 回注 → retry → 收敛
severity含义处理
violation违反契约（枚举/格式/敏感）必须修
drift非规范名（sym → ticker）应修
unverifiable无约束锚定报告，不硬失败

两个 ground truth：① 契约自身（deterministic）；② 运行时环境（tsc / pytest / eslint，可插拔）。LSP 是来源之一，不是替代品。

第三幕 · §3

封闭世界 vs 开放世界

§2 讲清了构成。本节讲为什么开放世界必须四块齐全——尤其为什么仅有 Inject（户口簿那半）不够。

维度户口簿（封闭）SemanticAnchor（开放）
输入可枚举别名无边界 prompt + 任意代码库
约束来源策展字典环境派生 + 会话累积
命中率高；miss 是异常低；miss 是常态
作用点输入解析（resolve）行动守门（verify）
验证真理协议自洽环境裁决

三个根本转移

  1. 作用点：输入解析 → 行动守门
  2. 来源：策展字典 → 环境派生
  3. 验证真理：协议自洽 → 环境裁决

户口簿是 SemanticAnchor 在封闭世界、declared-only 的退化特例。封闭世界 Inject≈保证；开放世界必须补 Gate。

第三幕 · §4

多 Agent 与 bundle 传递

bundle 不只是省 context——它是 Planner → Coder 的标准 handoff 协议。

Planner   bind_constraints(aliases)  ──▶  bundle
Coder     读 bundle 生成 usages
Gate      verify_usage(usages)         ──▶  feedback → Coder retry

没有标准 bundle，Planner 解析到的 ticker / order_side 契约在 handoff 时丢失，Coder 退回 prompt 软约束 → 语义漂移重现。

第四幕 · §5

四动词 = 构成的 MCP 映射

4 个工具是 §2 四块的操作化，不是另起一套概念。

工具对应构成性质职责
resolve2.1 锚 · 解析面best-effort别名 → 规范 id
get_constraint2.2 链 · 读契约查询取完整 ConstraintUnit
bind_constraints2.3 抛锚best-effort打包 bundle + 注入指引
verify_usage2.4 绷紧must-have契约 + 环境裁决 → feedback

户口簿 16 个工具是产品面，不进开源协议。

第四幕 · §6

走读：量化限价报单

任务：Implement a limit buy order submission: ticker symbol, order side, quantity, and trading account id.

步骤动作结果
1Planner bind_constraints4 实体 resolved → bundle

Naive 基线（无 bind、无 loop）：同样生成物 → 7 错误全部 shipped。运行 npm run demo 可复现。

第五幕 · §9

设计原则 + 非目标

原则

  1. 结构化契约优先于 Prompt
  2. 注入是优化，守门是保证
  3. miss 是常态，不是错误
  4. 只约束引用，不约束逻辑（窄腰）
  5. 协议最小化 — 4 个动词

非目标

不做

业务字典 · 规则引擎 · 低代码 Schema · 完整 agent runtime · 16 工具产品面

做

引用级约束协议 · 4 动词 MCP · 量化碰撞测试 · 工程验证报告
